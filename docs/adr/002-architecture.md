ADR-002: Backend Modular Monolith Architecture

- Status: Accepted
- Date: 2026-11-13

Context

Backend на NestJS. Требуется разделять функциональность на независимые модули, ограничивать связанность и упрощать тестирование. Микросервисы пока создают избыточную сложность; выбран модульный монолит.

Decision

Backend реализуется как Modular Monolith на NestJS. Все модули работают в одном процессе и используют общую PostgreSQL в зависимости от окружения (разработка, тесты, продакшн).

1. Структура модулей

Каждый модуль организован единообразно:

- Controllers — обработка HTTP-запросов и взаимодействие с клиентом.
- DAO (Persistence) — инкапсуляция доступа к данным через Prisma.
- Use Cases — сценарии приложения, бизнес-логика и координация операций.
- Tests — модульные и интеграционные тесты.
- DTO — выходные DTO для API и Swagger.
- Module — регистрация компонентов и зависимостей NestJS.

Входные DTO и Zod-схемы переиспользуются из "shared".

2. Разделение ответственности

Controller принимает запрос и делегирует выполнение Use Case. Use Case выполняет сценарий и координирует операции. DAO отвечает за работу с БД и не содержит бизнес-логики. DTO описывает формат выходных данных API. Module отвечает за регистрацию компонентов и зависимостей.

3. Тестирование

Vitest:

- Unit tests — с mock-зависимостями.
- Integration tests — с тестовой PostgreSQL.

Consequences

Плюсы: разделение ответственности, единая структура модулей, снижение связанности, удобство тестирования.

Минусы: общий процесс и база данных; границы модулей и публичные интерфейсы требуют контроля; независимое масштабирование модулей невозможно без изменения архитектуры развёртывания.

---

Frontend Architecture

Frontend использует Feature-based архитектуру на React.

1. Структура приложения

- "features" — функциональные области приложения, содержащие относящиеся к ним страницы и логику.
- "common" — общая инфраструктура, API-клиент и общие типы.
- "components" — общие компоненты интерфейса и UI-компоненты.
- "hooks" — переиспользуемые React hooks.
- "App.tsx" — маршрутизация и подключение провайдеров приложения.

2. Организация features

Функциональность разделяется по предметным областям:

- "auth" — авторизация и регистрация, соответствующие страницы и hooks.
- "user" — пользовательская функциональность и страницы профиля.

Логика, относящаяся к конкретной функциональной области, располагается внутри соответствующего feature.

3. Работа с данными

- TanStack Query — управление серверным состоянием и асинхронными запросами.
- React Hook Form — управление формами.
- Zod — валидация данных.
- Входные схемы и типы переиспользуются из "shared".
- Общий API-клиент располагается в "common/api".

4. UI и маршрутизация

React Router отвечает за маршрутизацию. Tailwind CSS используется для стилизации, shadcn/ui — как основа переиспользуемых компонентов интерфейса.

5. Принципы

- Разделение функциональности по features.
- Повторное использование общих компонентов и hooks.
- Размещение специфичной для feature логики внутри него.
- Общая инфраструктура не дублируется между features.
