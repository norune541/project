# ADR-001: Monorepo Architecture

- **Status:** Accepted
- **Date:** 2026-11-11

## Context

Проект содержит клиентскую и серверную части, которым необходимо использовать общие контракты данных и схемы валидации.

Для организации кода используется Monorepo с разделением приложения на независимые workspace-пакеты. Это позволяет централизованно управлять зависимостями, переиспользовать код и синхронизировать изменения между frontend и backend.

## Decision

Проект организован как Monorepo с использованием npm Workspaces.

Структура проекта:

```text
project/
  backend/
  frontend/
  shared/
```

### Backend

Серверная часть реализована на следующих основных технологиях:

- **NestJS** — серверный фреймворк, обеспечивающий модульную организацию приложения.
- **Prisma** — ORM для взаимодействия с базой данных.
- **Vitest** — Unit тесты
- **Supertest** — integration тесты

NestJS был выбран благодаря встроенному CLI, который упрощает создание модулей, контроллеров и других структурных элементов приложения. Модульная архитектура фреймворка помогает организовать код и поддерживать разделение ответственности. Дополнительную ценность предоставляет экосистема @nestjs, включающая интеграции для Swagger, Helmet и ConfigModule, что упрощает настройку документации API, HTTP security headers и конфигурации приложения.

Prisma используется как ORM благодаря предыдущему практическому опыту работы с ней. Знакомство с инструментом позволяет быстрее разрабатывать функциональность, использовать типизированные запросы и эффективно взаимодействовать с базой данных.

### Frontend

Клиентская часть реализована на следующих технологиях:

- **React** — библиотека для построения пользовательского интерфейса.
- **TanStack Query** — управление серверным состоянием, запросами и кешированием данных.
- **shadcn/ui** — набор переиспользуемых UI-компонентов.
- **react-router-dom** — Клиентская маршрутизация
- **openapi-fetch** — легковесный http клиент на основе fetch

shadcn/ui выбран благодаря наличию готовых переиспользуемых компонентов, которые сокращают время разработки пользовательского интерфейса и позволяют сосредоточиться на функциональности приложения.

Tailwind CSS используется для ускорения стилизации интерфейса благодаря utility-first подходу, позволяющему задавать стили непосредственно в разметке без необходимости создавать большое количество отдельных CSS-классов.

openapi-fetch выбран в качестве HTTP-клиента благодаря небольшому размеру, минимальной дополнительной абстракции над Fetch API и поддержке удобной настройки HTTP-запросов с автоматической типизацией swagger. 

TanStack Query используется для управления серверным состоянием, кеширования результатов запросов и синхронизации данных с backend.

### Shared

Пакет `shared` содержит общие Zod-схемы и сгенерированные swagger аннотации типов, используемые frontend и backend.
Схемы выступают единым источником определения структуры и правил валидации данных.
TypeScript-типы выводятся непосредственно из Zod-схем с помощью `z.infer`.

Frontend использует схемы для валидации пользовательского ввода, backend — для проверки входящих данных.

## Consequences

### Positive

- Единая структура репозитория для frontend и backend.
- Повторное использование Zod-схем и TypeScript-типов.
- Отсутствие дублирования общих контрактов.
- Синхронизация изменений между клиентской и серверной частями.
- Централизованное управление зависимостями через Bun Workspaces.
- Упрощение совместной разработки и настройки CI/CD.

### Negative

- Необходимость контролировать границы зависимостей между пакетами.
- Изменения общих схем могут затрагивать одновременно frontend и backend.
- CI/CD должен учитывать зависимости между workspace-пакетами.
- Необходимо следить, чтобы серверные зависимости не попадали в клиентскую сборку.
