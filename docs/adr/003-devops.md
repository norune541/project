ADR-003: DevOps и инфраструктура проекта

- Status: Proposed
- Date: 2026-11-13

Context

Проект организован как Monorepo на npm Workspaces и состоит из frontend, backend и shared-пакета.

Для локальной разработки и запуска приложения используется Docker Compose. GitLab CI выполняет проверки и сборку приложений.

Необходимо определить единый подход к контейнеризации, CI/CD, конфигурации окружения и развёртыванию приложения.

Decision

1. CI/CD — GitLab CI

GitLab CI используется для автоматизации проверок, сборки и развёртывания приложения.

Pipeline организуется по следующим этапам:

- Test — сборка shared-пакета, lint frontend и backend, unit и integration tests.
- Build — сборка frontend и backend.
- Publish — сборка Docker images и публикация в GitLab Container Registry.
- Deploy — развёртывание приложения на целевом сервере с использованием Docker Compose.

Сборка и публикация Docker images выполняются из корня репозитория, поскольку проект использует npm Workspaces.

Публикация образов и развёртывание должны выполняться после успешного прохождения проверок и сборки.

2. Docker

Docker используется для контейнеризации компонентов приложения.

Для каждого приложения предусмотрен отдельный Dockerfile:

- "backend/Dockerfile" — сборка и запуск NestJS backend.
- "frontend/Dockerfile" — сборка React frontend и запуск через Nginx.

Используются multi-stage builds, чтобы отделить этап сборки от production-окружения и не включать инструменты разработки в финальные образы.

Для запуска сервисов используется Docker Compose.

Основные сервисы:

- PostgreSQL — основная база данных приложения.
- Backend — NestJS API.
- Frontend — статические файлы React-приложения, обслуживаемые Nginx.

Для PostgreSQL используется Docker volume, обеспечивающий сохранение данных между перезапусками контейнера.

3. Nginx

Nginx используется как web-сервер для frontend и reverse proxy для backend API.

Его обязанности:

- Раздача статических файлов собранного React-приложения.
- Обработка клиентской маршрутизации через fallback на "index.html".
- Проксирование запросов "/api/" на backend.
- Передача HTTP-заголовков с информацией о клиентском запросе.

В текущей конфигурации Nginx принимает HTTP-соединения на порту "80". Настройка HTTPS должна быть предусмотрена при публикации приложения в production-окружении.

4. Конфигурация и секреты

Конфигурация приложения передаётся через environment variables.

Секреты и переменные окружения production не хранятся в Git-репозитории.

Для CI/CD используются GitLab CI/CD Variables с соответствующими настройками Masked и Protected для чувствительных значений.

Примеры конфигурации хранятся в ".env.example".

5. Database migrations

Для управления изменениями схемы PostgreSQL используется Prisma Migrate.

В production применяются уже созданные миграции через "prisma migrate deploy".

Миграции должны выполняться в рамках процесса развёртывания до запуска новой версии backend.

Заполнение production-базы тестовыми или начальными данными не должно быть неявной частью каждого запуска приложения. Seed должен запускаться контролируемо.

Consequences

Плюсы:

- Единый процесс проверок и сборки через GitLab CI.
- Воспроизводимое окружение благодаря Docker.
- Разделение frontend, backend и базы данных на отдельные контейнеры.
- Централизованное хранение Docker images в GitLab Container Registry.
- Упрощение развёртывания приложения через Docker Compose.
- Сохранение данных PostgreSQL между перезапусками контейнеров.

Минусы:

- Необходимость настройки GitLab Runner и доступа к Docker.
- Необходимость управления секретами и переменными окружения.
- Дополнительные требования к серверу для production-развёртывания.
- Необходимость контролировать совместимость миграций с предыдущей версией приложения.
